제안된 변경에 대해 권한 있는 주체가 내리고 기록한 결정입니다.

## 이 단계에서 생기는 문제

검토자가 제안과 근거를 확인한 뒤 승인 여부를 결정합니다. 누가 결정했는지 설명하고 추출 결과가 검토 절차를 우회하지 못하도록 합니다.

## 한 메모를 따라가 보기

검토자는 메모를 실제로 읽을 수 있어야 하며 후보와 근거를 비교합니다. MCP로 후보를 제출한 AI가 이 승인을 대신하지 않습니다.

## 개념과 구현을 구분하기

F4는 검토자 정책 집행을 다룹니다. 접근 검사가 구현되어 있어도 의도한 모든 정책 제한이 집행된다는 증거는 아닙니다.

승인 시 그래프 트랜잭션 안에서 근거의 활성 상태와 접근 권한을 다시 확인한 뒤 정식 기록으로 반영합니다.

## 구현이 지켜야 할 경계

- MCP는 승인·거절할 수 없습니다. 대기 제안에 충돌하는 결과를 만들 수 없습니다. 현재 근거 ACL로 권한을 판단합니다.

## 입력·출력·데이터 책임

- 타입 지정 후보, 생성자 접근 맥락, 검토자 식별과 결정.
- 불변 승인·거절 결과 하나와 승인 시 정식 기록.
- Proposal 식별·내용, SUPPORTED_BY 계보, Approval 이력.

## 비슷해 보이는 개념 비교

| 구분 | 답하는 질문 / 역할 | 주의할 경계 |
|---|---|---|
| 후보 제출 | 이런 내용을 받아들이자고 요청 | 근거와 구조를 갖춤 |
| 승인 | 권한 있는 검토자가 후보를 받아들임 | MCP 제출 권한과 별개 |

### AI가 후보를 만들고 전송했다면 승인까지 완료된 것인가요?

아닙니다. 후보 제출과 별도 검토는 다른 단계입니다. 검토 시점의 근거 접근 권한과 승인 이력이 필요합니다.

### 코드나 테스트 파일이 존재한다는 것만으로 이 기능을 믿어도 될까요?

아닙니다. 아래 연결된 테스트의 실행 결과·리비전·환경·검증 범위를 확인해야 합니다. 열린 문제와 보류 범위를 제외하고 판단하며, 이 문서 탐색은 운영 테스트를 실행하지 않습니다.
