제안된 변경에 대해 권한 있는 주체가 내리고 기록한 결정입니다.

## 이 단계에서 생기는 문제

검토자가 제안과 근거를 확인한 뒤 승인 여부를 결정합니다. 누가 결정했는지 설명하고 추출 결과가 검토 절차를 우회하지 못하도록 합니다.

## 한 메모를 따라가 보기

검토자는 메모를 실제로 읽을 수 있어야 하며 후보와 근거를 비교합니다. MCP로 후보를 제출한 AI가 이 승인을 대신하지 않습니다.

## 개념과 구현을 구분하기

F4는 검토자 정책 집행을 다룹니다. 접근 검사가 구현되어 있어도 의도한 모든 정책 제한이 집행된다는 증거는 아닙니다.

승인 시 그래프 트랜잭션 안에서 근거의 활성 상태와 접근 권한을 다시 확인한 뒤 정식 기록으로 반영합니다.

## 구현이 지켜야 할 경계

이 문서에서 참조하는 **승인 (Approval)**의 구현 책임입니다. 개념이나 학습 단계 자체를 별도 서비스로 뜻하는 것은 아닙니다.

- 승인 자체가 외부 Action을 실행하지 않습니다.

## 입력·출력·데이터 책임

이 문서에서 참조하는 **승인 (Approval)**의 구현 책임입니다. 개념이나 학습 단계 자체를 별도 서비스로 뜻하는 것은 아닙니다.

입력: 검토 식별, 결정, 이유, 허용 근거.

출력: 승인·거절 결과 하나.

보유 데이터: 정확히 하나의 관리 부모를 가진 결정 기록.

## 비슷해 보이는 개념 비교

| 구분 | 답하는 질문 / 역할 | 주의할 경계 |
|---|---|---|
| 후보 제출 | 이런 내용을 받아들이자고 요청 | 근거와 구조를 갖춤 |
| 승인 | 권한 있는 검토자가 후보를 받아들임 | MCP 제출 권한과 별개 |

## 텔레그램에서 검토하고 승인하기

현재는 개인 텔레그램 봇을 사람의 검토 화면으로 연결할 수 있습니다. 새 제안 알림에서 **검토하기**를 누르면 변경 내용과 원문 근거가 담긴 전체 검토 자료를 받습니다. 읽고 **내용 확인 · 승인** 또는 **반려**를 누르면 기존 지식 서비스가 권한과 상태를 다시 확인하고 결정 이력을 남깁니다. 봇과 대화하는 AI가 대신 승인하는 구조는 아닙니다.

예를 들어 “프로젝트는 Neo4j를 사용한다”는 후보가 오면, 어떤 문서의 어느 버전에서 나온 말인지 확인한 뒤 승인합니다. 제안 승인은 정식 지식으로 반영할 수 있지만, 외부 작업(Action) 승인은 실행 허가만 기록합니다. Notion 페이지 생성 같은 실제 작업은 별도의 권한 있는 실행기가 담당합니다.

봇을 처음 만들었거나 `/start`만 보냈다고 연결이 완료되지는 않습니다. 로컬 설정 프로그램에 토큰을 입력하고, 그 프로그램이 출력하는 일회용 링크의 `?start=` 값으로 본인 계정을 연결해야 합니다. 연결은 숫자 계정 ID와 개인 대화에 묶입니다. 다른 사람, 다른 메시지, 만료된 버튼, 검토 후 내용이 바뀐 요청은 승인할 수 없습니다.

현재 실행 명령은 터미널에서 계속 동작합니다. 창을 닫아 프로세스가 종료되거나 맥이 잠들면 처리가 멈춥니다. 터미널 창은 텔레그램의 필수 조건이 아니라 이 실행 방식의 조건이며, 백그라운드 서비스 배포는 별도 작업입니다. 프로그램과 Neo4j가 실행 중일 때 승인 요청을 처리합니다. 이 봇은 원본 동기화나 지식 추출을 자동으로 시작하지 않습니다.

구현과 격리된 DB 승인 테스트는 준비되어 있지만, 각 사용자의 실제 알림 수신은 봇 토큰·본인 연결·실행 상태를 따로 확인해야 합니다. 텔레그램 연결 자체가 기존 검토자 정책의 모든 감사 항목을 해결했다는 뜻은 아닙니다.

### AI가 후보를 만들고 전송했다면 승인까지 완료된 것인가요?

아닙니다. 후보 제출과 별도 검토는 다른 단계입니다. 검토 시점의 근거 접근 권한과 승인 이력이 필요합니다.

### 코드나 테스트 파일이 존재한다는 것만으로 이 기능을 믿어도 될까요?

아닙니다. 아래 연결된 테스트의 실행 결과·리비전·환경·검증 범위를 확인해야 합니다. 열린 문제와 보류 범위를 제외하고 판단하며, 이 문서 탐색은 운영 테스트를 실행하지 않습니다.
