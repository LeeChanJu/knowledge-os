## Follow evidence, not just arrows {#begin}

This lesson follows one fictional memo through the system. At each step, ask three questions: what arrives, what is preserved, and what does not happen automatically? A pipeline picture can make everything look inevitable. The actual architecture contains explicit boundaries between observing a file, proposing knowledge and accepting a change.

## What you will learn {#objectives}

**Prerequisites:** Start Here and Source of Truth vs System of Context. You should already know that Drive owns the original while Knowledge OS preserves evidence and context.

You will learn to reconstruct a statement's lineage, distinguish an unchanged retry from a new observation, and explain why updating or deleting a document differs from correcting accepted knowledge. You will also practice identifying an unsupported extraction.

## Our fixed teaching record {#example}

D1 is the fictional **“Joule Studio and agent communication review memo.”** Its V1 text says we are considering Joule Studio for agent development in the SAP ecosystem. It mentions A2A as agent communication, but explicitly does not establish that Joule Studio uses A2A. C1 is the passage containing these sentences.

D1, V1, C1, P1 and A1 are readable educational labels. Actual IDs are generated by repository rules. This is a walkthrough of responsibilities, not a transcript of a live Drive run or proof of product relationships.

## Observe and prepare the input {#observe}

The connector reads an authorized source observation. Its job is to translate provider-specific information into the shared manifest contract: identifiers, revisions, content, metadata, permissions and relevant deletion observations. A provider SDK does not define the canonical knowledge model.

Parsing turns a supported format into text. Chunking divides that text into individually addressable evidence. They solve different problems: reading a PDF is not the same as choosing the passages used for retrieval. Actual adapters prepare text before the graph ingestion writes its version; the following lineage diagram shows ownership, not a claim that parsing always occurs after persistence.

The Source binds the integration to a stable connector identity. Checkpoints describe committed progress. An unchanged retry must not manufacture another semantic history merely because the process ran again.

## Preserve the evidence chain {#lineage}

```flow
Source S1 | Which observed source and connector binding did this come from?
Document D1 | Which logical provider document is it across edits?
DocumentVersion V1 | Which exact state, metadata and authorization snapshot was captured?
Chunk C1 | Which exact passage belongs to that immutable version?
Assertion A1, only after review | What accepted statement is supported by that passage?
```

A Document is like the identity of a book; a Version is a particular edition; a Chunk is an addressable passage. The analogy stops where the implementation uses deterministic processing and content identities rather than physical page numbers. Renaming a book does not necessarily make it a different book, and a changed edition does not erase the previous edition.

Pause at C1. You should be able to answer “which file?” and “which state of that file?” separately. A citation to D1 alone cannot tell a reviewer whether the quoted wording belonged to V1 or V2.

F1 binds metadata hashes to the title and URI actually persisted in DocumentVersion. Its current scoped regressions pass. F6 remains an open finding about chunk size bounds; a configured limit is not evidence that every input respects it.

## Propose meaning without inventing support {#proposal}

A separate author or extraction provider can turn C1 into a candidate. The repository supplies versioned ontology and prompt context, but an automatic extraction provider is not assumed active. Embeddings are another separate boundary: they annotate eligible evidence for similarity retrieval, not transform text into accepted knowledge.

Suppose candidate P1 says **Joule Studio USES A2A**. This uses registered Technology endpoints and a permitted predicate, but C1 does not establish use. Structural validity is not evidence sufficiency. The reviewer should reject P1. No A1 should be created from that rejected candidate.

For a positive contrast, imagine a later educational V2 explicitly says “This pilot uses Joule Studio.” A proposal about the fictional pilot may use an allowed Project USES Technology relationship if the exact V2 passage supports it. The reviewer still needs current access and the approval path. This hypothetical text is not a claim about a real project.

| Stage | What it means | What it does not mean |
| --- | --- | --- |
| Extraction | Produce a structured candidate | Establish that it is true |
| Ontology validation | Check registered types and endpoints | Read and prove the source's meaning |
| Proposal | Preserve a reviewable request with evidence | Insert canonical knowledge directly |
| Approval or rejection | Record an authorized decision | Give an agent unlimited write authority |

## Retrieve and reconstruct {#retrieval}

A caller might search for “Joule Studio,” inspect an authorized entity, then request exact supporting Chunk IDs. Evidence can be followed from the statement back through C1, V1, D1 and S1. The bundle returns the immutable evidence identity while checking current authorization.

Full-text and semantic retrieval produce candidates; current hybrid retrieval combines those two sources. Direct neighbor reads offer bounded graph context. They are separate interfaces, not an automatically executed reasoning plan. Production embedding population is inactive in the documented evidence, so having a vector index does not imply the example has searchable embeddings.

A person or external model then uses the returned context. Knowledge OS supplies evidence, not a guarantee that the consumer will reason correctly. A useful answer should identify its support and distinguish what the memo says from what it leaves unknown.

## Revisit the same document through time {#timeline}

```flow
Day 1: capture V1 / C1 | Preserve the original observation; reject unsupported P1.
Day 2: observe V2 / C2 | Keep D1 identity and retain V1; review any new candidate separately.
Day 3: correct accepted meaning | Use governed supersession where applicable; preserve the old record and evidence.
Day 4: observe deletion | Record a tombstone, update current lifecycle, preserve historical lineage.
Retry Day 4 | Replay the same observation deterministically rather than invent another deletion.
```

Source versioning describes document states. Supersession describes a governed replacement of accepted knowledge. A change in one does not automatically perform the other. Domain validity, observation time and system recording time answer different questions; not every object carries the same time fields.

Deletion also differs from erasure. Preserving history does not promise continued retrieval: the current lifecycle and permissions still govern reads. F2's executed regressions cover deterministic deletion replay and related correction scope, not every integration failure. New temporal implementation exists, but this lesson does not promote it to a fresh VERIFIED claim.

## From context to an Action {#action}

A team may decide to record its review in Notion. An agent can submit a governed Action request. Approval records a decision; execution requires a separately authorized adapter and a pre-execution claim. The adapter records its result after contacting the System of Record. Knowledge retrieval alone authorizes none of these changes.

Outcome records may inform later context, but the picture does not imply an automatic learning loop. The current bounded Notion executor is narrower than a general autonomous agent platform. F4 and F8 remain open around governance policy and graph/audit failure behavior.

## Current implementation and limits {#current}

**CURRENT v0.1:** manifest ingestion, version/Chunk lineage, deterministic identity, exact evidence reads, Proposal/Approval and bounded retrieval interfaces are implemented. F1 and F2 were rerun in isolated real Neo4j databases for their declared scopes.

**TARGET / DEFERRED:** automatic extraction and production embedding providers, advanced resolution and A2A integration are not activated by this walkthrough. F3–F8 and release acceptance remain open. The examples perform no production operations from this documentation page.

> **Common misconception:** “Capturing a document automatically creates accepted knowledge.” Ingestion preserves evidence. A separate candidate and authorized review are required for canonical statements.

## Explain it back {#checks}

```question
Why must a reviewer reject P1 even if it passes the ontology validator? What would count as better evidence?
---
V1 only co-mentions the technologies and explicitly leaves use unestablished. A passage explicitly supporting the proposed relationship, with exact evidence identity and authorized review, would be needed. A valid predicate alone is insufficient.
```

```question
If an old answer cites C1 and D1 now has V2, should C1 be moved to V2? Explain the consequence.
---
No. C1 belongs to V1. Moving it would rewrite what supported the old answer. New evidence should have its own version and Chunk identity; accepted meaning is corrected through governance when needed.
```

```question
After a deletion, can both “history is preserved” and “the caller cannot retrieve the evidence” be correct?
---
Yes. Retention preserves lineage for accountable history. Current lifecycle and authorization determine whether an evidence read is permitted. Storage retention is not an access grant.
```
